# Source migration tiers

Generated by `tools/audit_sources.py`, cross-checked against
`docs/imin_from_code.md`. Task 13-16 follow this table.

**Tiering criterion (updated).** An earlier draft of this task tiered
sources on "has a join key AND an unambiguous recovered i_min". The second
half is obsolete: Task 10 established that i_min is authoritatively
readable straight from the legacy code for every one of the 13 sources
(`docs/imin_from_code.md`), so it no longer distinguishes sources from one
another. **Tier-1 now means solely: the published rows carry a usable
`(capture, frame_idx)` join key**, as tested by `gsmp.schema.has_join_key()`.
The i_min column below is retained for convenience (so a Task 15/16
implementer has tier and threshold in one place) but plays no role in the
tier assignment itself.

**tier-1** — published rows carry a usable `(capture, frame_idx)` join key
(`gsmp.schema.has_join_key()` returns `True`). These are migrated onto
SourceSpec + the generic runner, and each one ships with a passing
`tools/regress.py` run recorded in its commit message.

**tier-2** — no join key. These are wrapped verbatim: the original iterator
is moved into `src/gsmp/sources/<name>.py` unchanged and only given a
SourceSpec for metadata. Their internal filtering logic is NOT refactored,
because there is no way to prove the refactor preserved it.

## Known tier-2 causes

- `feats` — published with the full 30-column schema, but `frame_idx` is
  NULL in all 1363 published rows, so there is no usable join key. This is
  not an oversight: the source is filtered on force (`|f_z| >= 0.4 N`,
  `legacy/reprocess_feats.py:18,113`), not on pixel/contact intensity, so
  there was never a pixel-domain `frame_idx` to carry through in the first
  place. It has no `i_min` to recover, by design.
- `fota_labeled` — published with the older 26-column schema
  (`gsmp.schema.LEGACY_26_SOURCES`), which has no `frame_idx` column at
  all. There is no column to test for a join key against.
- `fota_unlabeled` — same 26-column schema defect as `fota_labeled`, so no
  `frame_idx` column exists to join on. Additionally, `fota_unlabeled` was
  post-processed by the v9 channel-order fix after its initial ingest
  (`legacy/swap_fota_unlabeled.py` swaps R<->B in-place on the already
  -published shards; `legacy/fix_channel_order.py:8,49` lists
  `fota_unlabeled` explicitly as "full dataset BGR"; `legacy/finalize_v9.sh`
  orchestrates the swap and republish). So even if a join key existed, the
  published bytes reflect a one-shot in-place channel swap applied after
  the original ingest, and that intermediate state is not reproducible from
  the current raw data.
